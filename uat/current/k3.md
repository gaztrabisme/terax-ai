# UAT: k3
Design: docs/design.md sections 5.1 to 5.5 and 6.5 (K3.2, K3.3, K3.4); principles served: 10 (measured, then built), 7 (the work is visible and attributable)
Required units: none
Fixture variant: clean; fault:unwritable-pi-dir for row 8 only
Platform/shell: macOS; integrated zsh fixture
Target phase: current
Row deadline: 90 per row (a deadline bounds a stuck test, it is not a latency claim)

1. Given a fresh fixture project that has never been launched with the `--uat` flag
   When I launch the app normally, type "List the files in this folder in one line" into `pi composer` and press Enter, and wait for the completed turn
   Then the completed turn with its answer is visible, and the project `.pi/` directory contains no `uat-snapshot.json`, no `uat-status.json`, no `uat-refresh.json` and no `logs/uat.jsonl`
   Shot: 01-flag-off-clean.png; Evidence: the file-absence listing for those four paths is recorded in the result file
2. Given the same clean flag-off run
   When I resolve `Settings` by accessibility name, click the centre of its rect, then click it again
   Then Settings opens and closes normally; no UAT status control, banner or retry control appears anywhere in the window
   Shot: 02-flag-off-settings.png
3. Given a previous flagged run of the same project whose `uat-snapshot.json` hash and `runId` were recorded at quit time
   When I quit through the app's own Quit action, relaunch the same project without the flag, and send one turn from `pi composer`
   Then the historical `uat-snapshot.json` is byte-identical to the recorded hash and its `runId` still names the earlier launch, not this one; the driver refuses it as current evidence
   Shot: none; Evidence: shasum of `<project>/.pi/uat-snapshot.json` before and after, plus both runId values recorded
4. Given the app relaunched with the `--uat` flag on the same project
   When I request a fresh snapshot, resolve [uat:settings-button] from it and click the returned centre
   Then Settings opens; repeat the resolve-and-click after moving the window, after resizing it and after changing zoom, and Settings opens each time
   Shot: 03-flag-on-targeting.png
5. Given the flagged run after each move, resize and zoom from row 4
   When I compare the snapshot's transformed bounds for [uat:settings-button] against its accessibility rect
   Then each of the four edges agrees within 8 macOS points in every case, and each click landed on the rect centre
   Shot: none; Evidence: the per-case bounds comparison table in the result file
6. Given the flagged run with a completed tool-bearing turn and the transcript scrolled so the last turn is partly out of view
   When I scroll the last turn's [uat:turn-fold] fully into view, refresh the snapshot and click the fold from the fresh coordinates
   Then the fold expands its tool rows; the driver waited for the new refresh nonce before clicking and refused the stale file
   Shot: 04-scrolled-target.png
7. Given the flagged run in its healthy state
   When I read the UAT banner [uat:uat-health] (label `UAT snapshot health`)
   Then it shows the current snapshot state with no error, `.pi/uat-status.json` records the fresh run, and `.pi/logs/uat.jsonl` grows one acknowledged line per refresh
   Shot: 05-health-banner.png; Evidence: the status JSON path and the log line count before and after one refresh
8. Given the flagged run with `<project>/.pi/` made unwritable for the app until three refreshes have failed
   When I read [uat:uat-health], then restore write permission and click [uat:uat-retry] (label `Retry`)
   Then [uat:uat-health] named the failure while the directory was unwritable, and after the retry click it reports a newer acknowledged snapshot that the next resolve-and-click accepts
   Shot: 06-retry.png

Break attempts (notes only): launch with the flag while a previous flagged instance is still quitting; click from a snapshot older than one refresh; resize during a refresh and confirm the driver refuses mixed-scale bounds; quit mid-refresh and confirm no torn snapshot file is left behind.
