# UAT: k14
Design: docs/design.md sections 3.6 and 6.5 (K14.1), 6.4 (R1.1, R1.3, R2.1, R2.2, R15.1); principles served: 1 (the disk is the truth), 5 (one implementation), 10 (measure and test)
Required units: K14
Fixture variant: fault:nonexistent agent executable, missing last-project path, unreachable endpoint (plus a clean launch pass after each correction)
Platform/shell: macOS
Target phase: future
Row deadline: 90 per row (a deadline bounds a stuck test, it is not a latency claim)

1. Given the fixture project with distinct global, project and explicit role, path and endpoint values
   When I launch it and wait until [uat:session-strip] reports the session ready
   Then `<project>/.pi/runtime.json` exists, written before pi spawned: it transcribes the four preparation steps `seed`, `render`, `root`, `wiki` with their statuses, the effective binary with its source, the agent dirs, and the orchestrator role's provider, model, thinking and endpoint; every credential value in the file reads `[redacted]`
   Shot: 01-launch-clean.png; Evidence: `<project>/.pi/runtime.json` checked for the step names and statuses and for the absence of any credential value
2. Given the launched project
   When I open Settings, read [uat:pi-check-panel] and click [uat:pi-first-run-check] (visible `Run first-run check`)
   Then each [uat:check-row] describes the last real launch: exactly the effective binary, the seeded runtime agent dir, the provider, model, thinking and endpoint, each with its source, agreeing row by row with runtime.json; no bundled template path passes as an effective value
   Shot: 02-first-run-rows.png
3. Given the report endpoint pointed at an unreachable fixture endpoint
   When I click [uat:pi-first-run-check] again, then restore the working endpoint and check once more
   Then the failed endpoint row names that endpoint and its error in the form `<endpoint>: <why> (<source>)`, and no other endpoint's success stands in for it; the restored check reads answered with its latency and source
   Shot: 03-endpoint-fail.png; Shot: 04-endpoint-restored.png; Evidence: both check runs' rows against the endpoint's own probe
4. Given the fixture's agent executable configured to a nonexistent path
   When I open the project's chat
   Then [uat:launch-error] stands reading `Launch failed: <exact failure>`; the strip and composer remain visible, the window is not blank, and nothing claims success
   Shot: 05-launch-error.png
5. Given the failed launch from row 4
   When I click [uat:open-launcher-log] (visible `Open log`)
   Then an editor tab opens `<project>/.pi/launcher.log` naming the failed step, and the failed attempt wrote no new runtime report
   Shot: 06-open-log.png; Evidence: `.pi/launcher.log` content plus the unchanged `<project>/.pi/runtime.json` hash across the failed attempt
6. Given the executable path corrected
   When I click [uat:new-session] (visible `New session`)
   Then the session launches normally and `<project>/.pi/runtime.json` is rewritten describing this successful launch with its steps OK
   Shot: 07-retry-launch.png; Evidence: the rewritten file's step statuses and binary record
7. Given project A opened with a used session, then quit through the app's own Quit action
   When I launch only by the dock icon (`open "$PRODUCT"` with no arguments)
   Then chat identifies A and the exact last session with draft and history intact; all secondary views open closed and no chooser interferes for the authorized project
   Shot: 08-dock-recovery.png; Evidence: the preferences registry lastProject, the session manifest lastSessionId and `.pi/launcher.log` for the same launch
8. Given only the registry's last project made unavailable by renaming its folder, with the app quit
   When I dock-launch again
   Then the picker stands naming the missing path (`Project not found: <path>`) with a visible `Choose folder` control; choosing project B opens B's conversation, never stale A content
   Shot: 09-picker-missing-path.png; Evidence: the registry still naming the missing path and B's session files after the pick

Break attempts (notes only, each with a shot or log line): point the agent executable at a directory and at a non-executable file and compare both banner texts (shot); rename the project while quit, dock-launch, restore it and dock-launch again (shot); delete then malformed-edit runtime.json before running the first-run check and read the reported fallback (log line); dock-launch on a registry that never recorded a project (shot).
