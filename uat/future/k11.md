# UAT: k11
Design: docs/design.md sections 3.4 and 6.5 (K11.1 to K11.3), 6.4 (R7.1, R7.2, R13.4); principles served: 1 (the disk is the truth), 2 (the project is the unit)
Required units: K11
Fixture variant: clean (section 6.2 fixture; named fault cases: an unwritable .pi/ui-state.json, a terminated fixture shell process, a corrupt session file)
Platform/shell: macOS; integrated zsh fixture
Target phase: future
Row deadline: 90 per row (a deadline bounds a stuck test, it is not a latency claim)

1. Given the fixture project freshly opened with no pi session yet
   When I type a grounded prompt into [uat:composer-input] and wait for the answer
   Then `<project>/.pi/sessions/` gains this session's file and `<project>/.pi/session-manifest.json` records it: lastSessionId, the exact project-relative path, cwd, createdAt and lastTurnId; no new session file appears under the agent dir
   Shot: none; Evidence: `<project>/.pi/session-manifest.json` and the session file its entry names
2. Given the manifest from row 1 with the Sessions view closed
   When I click [uat:sessions-button], then [uat:sessions-expand] (visible `Expand Sessions`), and read [uat:sessions-list]
   Then the list reads the project store first: row 1's session appears as a [uat:session-row] carrying its project-relative locator; the agent dir is only a fallback for older sessions
   Shot: 01-sessions-project-store.png
3. Given the seeded past session file containing RECOVER_QUARTZ_17
   When I type "RECOVER_QUARTZ_17" into [uat:sessions-search] and click the past-session [uat:session-row]
   Then the active session changes to that saved session id ([uat:session-strip] identifies it) and the transcript scrolls to the exact prompt holding the marker
   Shot: 02-past-session-hit.png; Evidence: the manifest's lastSessionId after the hit and the session file opened
4. Given the same restored session
   When I type a phrase from the current session's first turn into [uat:sessions-search] and click its [uat:session-row]
   Then the active session stays that same session and the exact current turn scrolls into view; repeated row selections key on the row's identity, never its list position
   Shot: 03-current-session-hit.png
5. Given a query typed into [uat:sessions-search]
   When I close the Sessions panel, quit through the app's own Quit action and relaunch the project
   Then the search box returns with the saved query and no stale hits render: the view passes through its loading state into fresh results, and every chat tab reopens with secondary views closed and the sidebar collapsed
   Shot: 04-query-survives-restart.png; Evidence: `sessionsQuery` in `<project>/.pi/ui-state.json` with `sidebarVisible` false
6. Given the R7.2 fixture variants in turn: loading, empty, no matches, missing project, corrupt session file
   When I open Sessions in each variant and read [uat:sessions-list]
   Then each variant shows its own named state or error (loading indicator, empty notice, no-match notice, missing-project error, corrupt-file error naming the unreadable file) and never the previous variant's hits
   Shot: 05-session-states.png; Evidence: the named corrupt and empty fixture files beside each screenshot
7. Given Board width 360 CSS px set with [uat:panel-resize] (`Resize Board panel`) on project A and 420 CSS px on project B, plus a typed query on A
   When I quit and relaunch
   Then visibility is never restored: every chat tab opens with Board closed and the sidebar collapsed; opening Board on each project restores its own remembered width from its own ui-state file, and the pre-file localStorage layout bucket is imported once, then ignored
   Shot: 06-widths-not-visibility.png; Evidence: `views.board.widthCss` 360 and 420 in the two projects' `<project>/.pi/ui-state.json`
8. Given `<project>/.pi/ui-state.json` made unwritable and a new query typed into [uat:sessions-search]
   When the pending write fails
   Then the [uat:storage-error] banner stands under the tab edge reading `Storage error: <project>/.pi/ui-state.json` with [uat:storage-retry] (visible `Retry save`); the pending value is not silently saved
   Shot: 07-storage-error.png; Evidence: the file still holding the old value while the banner stands
9. Given the banner from row 8 with writability restored
   When I click [uat:storage-retry]
   Then the banner clears and the flushed `<project>/.pi/ui-state.json` holds the pending query; nothing else was dropped
   Shot: 08-storage-retry.png; Evidence: the file content after the retry
10. Given a chat draft typed into [uat:composer-input] and an editor tab holding an unsaved buffer
    When I quit through the app's own Quit action and relaunch the project
    Then the same tabs reopen under their stable ids, the draft returns ready in [uat:composer-input], and the editor tab shows `Unsaved, recovered` above its restored buffer before any Save
    Shot: 09-stable-drafts-recovered.png; Evidence: `.pi/drafts/<tab-id>.md` and the matching metadata files named by the same stable tab ids, including the editor buffer's
11. Given the recovered editor buffer while its backing file changes on disk
    When I press Mod-S in that tab, scoped to [uat:editor-tab]
    Then the save refuses with the visible `Save refused: <path> changed on disk since this buffer was last saved` text naming the disk path and the kept buffer's draft path; the buffer stays open with its content
    Shot: 10-editor-conflict.png; Evidence: the buffer's draft file still holds the unsaved text and the on-disk file is unchanged by the refused save
12. Given the zsh fixture terminal with completed blocks `echo uat-k11-journal` and `false`
    When I read [uat:exit-dot-ok] on the first [uat:terminal-block] and [uat:exit-dot-fail] on the second
    Then the first block records exit 0 with its output and duration and the second records exit 1
    Shot: 11-journal-blocks.png; Evidence: `<project>/.pi/terminal/<terminal-id>/blocks.jsonl` and the per-block `.ansi` output files agreeing with the screen
13. Given the project quit and reopened after those completed blocks
    When I click the history trigger (AX `List terminal history`) and then [uat:terminal-history-reopen] scoped to the saved terminal id
    Then a fresh shell opens with the recovered blocks: captured command, output, exit status and duration agree with the journal files, and the seeded 256-character command still carries its `Truncated command` marker
    Shot: 12-reopen-history.png; Evidence: the reopened block values equal to the `.pi/terminal/<terminal-id>/blocks.jsonl` records
14. Given the separate interrupted fixture whose recorded shell process was terminated by killing only that recorded PID
    When I reopen that terminal's history with [uat:terminal-history-reopen]
    Then the unfinished block is marked `interrupted / exit unknown`, [uat:block-rerun] is disabled on it so it cannot re-send, and the completed blocks still rerun normally
    Shot: 13-interrupted-block.png; Evidence: the journal's `interrupted` record for that block id and the exact killed process record

Break attempts (notes only, each with a shot or log line): make `.pi/` read-only mid-session and confirm the banner names the failing path until Retry succeeds (log line); delete the session file behind a manifest entry and search for it; kill the recorded shell PID of an already reopened history and confirm no duplicate recovered blocks (shot); rename the drafts directory before relaunch and confirm the editor refuses the conflict instead of overwriting (shot).
