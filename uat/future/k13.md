# UAT: k13
Design: docs/design.md sections 3.4 and 6.5 (K13.1, K13.2), 6.4 (R8.1, R8.2, R11.1, R11.2); principles served: 1 (the disk is the truth), 2 (the project is the unit), 9 (panes contain blocks)
Required units: K13
Fixture variant: clean (section 6.2 fixture with sample-a.png; named fault cases: attachments exceeding 4194304 bytes, a streaming-held send, an externally edited then deleted artifact file)
Platform/shell: macOS
Target phase: future
Row deadline: 90 per row (a deadline bounds a stuck test, it is not a latency claim)

1. Given the chat composer with no attachments
   When I paste `sample-a.png` into [uat:composer-input]
   Then a draft chip appears above the composer ([uat:attachment-chip]) showing the image and its path-backed draft location under `.pi/drafts/`, with a remove control (AX `Remove sample-a.png`)
   Shot: 01-draft-chip.png; Evidence: the draft file `.pi/drafts/<tab-sid>-<attachment-id>.png` byte-identical to `sample-a.png` and the draft metadata's attachments entry
2. Given the draft chip from row 1 without sending
   When I quit through the app's own Quit action and relaunch the project
   Then the chip returns in [uat:composer-input] bound to the same draft file path; the image still exists on disk and the chip shows its path, not a broken placeholder
   Shot: 02-chip-survives-restart.png; Evidence: the unchanged draft file and its metadata entry
3. Given the restored chip and a prompt typed into [uat:composer-input]
   When I click [uat:send-button] and wait for the acknowledged user turn
   Then the chip stands on that acknowledged turn as [uat:attachment-chip] scoped by the sent path; the staged copy at `.pi/attachments/<submission-id>-<attachment-id>.png` is byte-identical to the draft and `.pi/attachments/index.json` records `{submissionId,attachmentId,path,sha256,sessionId,turnId}` naming that turn
   Shot: 03-sent-binding.png; Evidence: the sha256 of the staged file equal to the draft's, and the index entry naming the acknowledged turn id
4. Given one draft chip already queued
   When I attach further images whose encoded total would exceed 4194304 bytes
   Then the composer shows the notice `Attachments would exceed the 4194304-byte (4 MiB) image budget`; the existing chip stays queued untouched and no partial attachment file is written
   Shot: 04-cap-notice.png; Evidence: the drafts directory holding no extra file from the refused image
5. Given a model whose image capability is unknown
   When I attach an image and then remove every chip
   Then the notice `This model may not accept images; pi decides what to do with them.` appears only while a chip is queued and is absent from the empty composer
   Shot: 05-vision-notice.png
6. Given a first prompt streaming and a second prompt carrying an attached image
   When I click [uat:send-button] while the first turn still streams and the RPC rejects the second before acceptance
   Then the failed submission stands visible with [uat:submission-retry] (visible `Retry submission`) scoped to its own submission id; no turn owns the image yet
   Shot: 06-failed-send.png; Evidence: `.pi/attachments/index.json` holding no entry for the failed submission id
7. Given the first stream released
   When I click [uat:submission-retry]
   Then only the retried submission's acknowledged turn binds the chip; the failed submission id never binds a later turn
   Shot: 07-retry-binds.png; Evidence: the index entry pairing the retried submission with its acknowledged turn and no others
8. Given a grounded answer whose document has no completed file yet
   When I read [uat:answer-actions] on that turn
   Then no viewer control exists: [uat:open-artifact] is absent until the model-written file is complete, while [uat:copy], [uat:copy-markdown] and [uat:open-in-editor] remain
   Shot: 08-no-file-no-control.png
9. Given the model has written the calibration HTML file
   When I click [uat:open-artifact] (visible `Open artifact`)
   Then the artifact panel opens with [uat:artifact-path] naming exactly that project file and [uat:artifact-frame] rendering `quartz-lantern`; the viewer offers no script-execution or save-before-view controls
   Shot: 09-open-artifact.png; Evidence: the artifact manifest's path and hash equal to the model-written file
10. Given the artifact panel open
    When I click [uat:artifact-copy-path] (visible `Copy path`) and paste into a scratch editor's [uat:editor-input]
    Then the pasted text is the artifact file's absolute path, the same file [uat:artifact-path] opens
    Shot: 10-copy-path.png
11. Given the artifact file externally edited, then deleted
    When I click `Refresh artifact` after the edit and read the panel after the deletion
    Then the refreshed frame renders the new contents; after deletion [uat:artifact-error] stands with a path-bearing load error and a `Retry artifact load` control, and restoring the file plus one retry clears it
    Shot: 11-refresh-then-error.png
12. Given a grounded answer with formatting
    When I click [uat:copy] and [uat:copy-markdown], paste each into a scratch editor's [uat:editor-input], then click [uat:open-in-editor]
    Then the two pastes equal the rendered answer and its exact Markdown source; Open in editor creates a nonempty `.md` file equal to that Markdown and reports it (visible `saved <name>`) with the file selected
    Shot: 12-open-in-editor.png; Evidence: the created answer file inspected before and after, byte-compared to the Markdown paste

Break attempts (notes only, each with a shot or log line): paste the same image twice across a failed send and its retry (shot); delete the draft file behind a queued chip and confirm the chip's missing-file state (shot); make `.pi/attachments/` unwritable before a send and read the standing error (log line); refresh the artifact while an external rewrite is in progress (shot).
